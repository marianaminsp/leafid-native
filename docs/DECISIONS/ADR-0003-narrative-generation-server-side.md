# ADR-0003: Move cultural narrative generation server-side

Date: 2026-08-06
Status: Accepted
Decision owners: Product/Engineering

## Context

LeafID's core value proposition is not gardening — it's a culture app: point the camera at a plant,
get name + species (table stakes) plus **Botanical Spirit, Ethnobotany, and Cultural Legacy** content
(the actual differentiator). While reviewing the launch-readiness checklist's "LLM keys embedded in
the binary" gap, tracing the full identification pipeline showed this was a bigger problem than
originally scoped: identification (name/species) already went through the `identify-plant` Supabase
edge function server-side, but the cultural narrative was generated by a **second, separate call
straight from the iPhone client** to Gemini and OpenRouter, using `GEMINI_API_KEY`/`OPENROUTER_API_KEY`
embedded in `Info.plist` — on every single successful scan, plus a third client-side call
(`geminiCulturalLegacyFact`) for enriching legacy scans that predate narrative content.

This meant the core content feature, not just the identification fallback, was exposed: anyone
extracting the keys from the shipped IPA could exhaust the shared Gemini free-tier quota or run up
OpenRouter charges under this project's account, with no server-side throttling possible since the
calls never touched Supabase.

There was also a live product goal in tension with this: keep API costs on free tiers wherever
possible. The narrative call already showed free-tier awareness (it deliberately used OpenRouter's
`openrouter/free` router first, with a code comment about avoiding Gemini's free-tier quota) — the
architecture just didn't protect that intent from client-side key extraction or give any way to
enforce it centrally.

## Decision

Add a new `supabase/functions/narrate-plant` edge function that generates the narrative server-side,
using the same provider order and prompts the client used to run itself (OpenRouter's free router
first, Gemini's free-tier direct API as fallback), reading `OPENROUTER_API_KEY`/`GEMINI_API_KEY` as
Supabase secrets instead of client build settings. It supports two modes: the default 5-field
narrative generation, and `mode: "legacy_fact"` for the single-fact enrichment on old scans
(`BotanyService.fetchLegacyFact`, replacing `geminiCulturalLegacyFact`).

`GEMINI_API_KEY`/`OPENROUTER_API_KEY` are fully removed from the client: `Info.plist`, the pbxproj
`INFOPLIST_KEY_*` build settings, `Secrets.xcconfig`, and `Secrets.local.xcconfig.example`. They no
longer need to exist anywhere in the shipped app.

## Consequences

### Positive

- Closes the "LLM keys embedded in binary" gap completely, not just for identification — the
  narrative content that's actually the product's differentiator is no longer extractable.
- Centralizes cost/free-tier policy in one place (the edge functions) instead of split between
  client build settings and two different call sites.
- No behavior change for users — same provider order, same prompts, same local textual fallbacks
  when both providers fail or the network call itself fails.

### Negative

- One more network hop (device → Supabase → provider, instead of device → provider directly) —
  acceptable since this call was already not on the identification critical path latency-wise.
- Does not resolve the sibling issue this surfaced: `identify-plant`'s own fallback chain still
  includes Plant.id (no real free tier) and a paid OpenRouter model as fallback 2 — tracked as a
  separate open gap in `docs/audit/qa-launch-checklist.html` ("Identification fallback chain
  includes non-free-tier providers"), since fixing it changes identification behavior/quality
  tradeoffs and deserves its own decision.

## Alternatives Considered

1. Leave narrative generation client-side, just document the exposure as an accepted risk.
   - Cheaper short-term, but the exposed keys are usage-billed credentials on a feature that runs on
     every scan — the risk compounds with growth, not shrinks.
2. Fold narrative generation into `identify-plant` itself instead of a separate function.
   - Simpler deployment (one function), but conflates two different failure/retry/timeout profiles
     (identification is on the critical path with a real chain of paid fallbacks; narrative is
     best-effort content with local textual fallbacks) — kept separate for clarity.

## Next Actions

1. Deploy `narrate-plant` via `supabase functions deploy narrate-plant` (not done in this session —
   requires Supabase CLI auth).
2. Set `OPENROUTER_API_KEY`/`GEMINI_API_KEY` as Supabase secrets if not already set from
   `identify-plant`'s existing configuration (same secret names, reused).
3. Decide on the Plant.id / paid-OpenRouter-model fallback question in `identify-plant` (see the
   linked QA-checklist gap) — separate decision, not covered by this ADR.
