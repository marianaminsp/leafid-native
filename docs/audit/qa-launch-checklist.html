Part B — Launch-readiness gaps

What's actually missing before this can ship, ranked by how badly it hurts if left as-is.

Blockers

App Store Connect will likely reject the build, or a core promised feature silently doesn't work.

No App Icon image

Resolved

AppIcon.appiconset/Contents.json now points at a real 1024×1024 PNG.

Consequence (was): App Store Connect validation rejects binaries without an icon at upload. Note: the file is named AppIcon-placeholder-1024.png — this unblocks build validation, but swap in the real branded icon before actual submission (redesign deliverable, not a QA item).
Assets.xcassets/AppIcon.appiconset/Contents.json

No PrivacyInfo.xcprivacy manifest

Resolved

PrivacyInfo.xcprivacy now exists, declares NSPrivacyTracking=false and UserDefaults as a required-reason API (reason CA92.1).

Note: NSPrivacyCollectedDataTypes is currently empty, but the app collects email, location, and photos via Supabase — that's the separate App Store Connect "Privacy Nutrition Label," not this manifest, but worth a deliberate pass before submission rather than leaving it as a default empty array.

Zero automated tests wired into the project

Resolved

A real unit-test target now exists, wired into the scheme's TestAction, with 8 real tests (Keychain round-trip, GPS formatting, free-tier gate logic, color hex round-trip) replacing the old boilerplate. The unedited UI-test boilerplate was removed.

Remaining gap: tests only run when someone remembers Cmd+U — see "No CI/CD pipeline" below, now the more load-bearing item.

Paywall has no real purchase mechanism

Blocker (if monetizing at launch)

PaywallView.onUpgradeTap defaults to a no-op closure, and none of its 4 call sites supply a real one. There is no StoreKit/IAP code anywhere in the app.

Consequence: if premium/monetization is meant to be live at launch, the upgrade button currently does nothing when tapped — a real user hits a dead end at the exact moment they're trying to pay you. If premium is post-launch, this is fine to defer, but the paywall shouldn't be shown to users yet in that case.
Views/Druid/PaywallView.swift:14,106-110

Auth tokens stored in UserDefaults, not Keychain

Mostly resolved

Session access token and refresh token now go through KeychainTokenStore (kSecAttrAccessibleAfterFirstUnlock) instead of UserDefaults.

Remaining gap: the OAuth PKCE verifier is still stored in UserDefaults (LeafID_nativeApp.swift:107,157,548). Lower severity — it's short-lived and deleted right after the token exchange completes — but worth finishing the migration for consistency.
LeafID_nativeApp.swift, Services/KeychainTokenStore.swift

High

Not an automatic rejection, but a real risk of rejection, a real security issue, or a real gap in your ability to operate the app post-launch.

Privacy policy exists but isn't linked or hosted

High

docs/PRIVACY_POLICY.md is a real, written (English + Spanish) policy — but nothing in the app UI links to it, and there's no confirmed public hosted URL.

Consequence: App Store Connect requires a live, publicly reachable privacy policy URL in the listing. The policy itself being well-written doesn't help if it's not reachable — this needs a hosting decision (GitHub Pages is already used for the password-reset redirect, so that pattern is available) and an in-app link, typically from Druid/Settings.

Google Sign-In without Apple Sign-In

High

Google OAuth is the only third-party sign-in option in the native app.

Consequence: App Review Guideline 4.8 requires offering Sign in with Apple when any other third-party login is offered. This is a common, specific rejection reason — worth resolving before first submission rather than discovering it via a rejection.

Third-party LLM API keys embedded in the shipped binary

Resolved

Turned out to be bigger than just the identify fallback: the cultural/historical narrative (Botanical Spirit, Ethnobotany, Cultural Legacy — the actual "culture app" content, not gardening tips) was being generated by a second, separate call straight from the iPhone client to Gemini/OpenRouter, using the same embedded keys, on every single successful scan.

Fix: new supabase/functions/narrate-plant edge function now generates that narrative server-side. GEMINI_API_KEY/OPENROUTER_API_KEY are fully removed from Info.plist, the pbxproj build settings, and Secrets.xcconfig — they're Supabase secrets now, never shipped in the app binary. Provider order and caching evolved further after this — see the next gap and ADR-0004.

Identification & narrative fallback chains, cost/resilience

Resolved

Live-testing narrate-plant right after deploy found it silently returning empty content: OPENROUTER_API_KEY was dead (401), and "openrouter/free" was never a real OpenRouter model ID. Separately, identify-plant still had Plant.id and a paid OpenRouter model in its fallback chain (both since removed).

Current state: identify-plant is Pl@ntNet → Gemini-direct (both free tier, Plant.id/paid-OpenRouter dropped). narrate-plant is Groq (new, reuses an already-configured but previously-unused GROQ_API_KEY secret) → Gemini-direct, with OpenRouter shelved (not deleted — kept in the file with a fixed real :free model ID, ready to re-enable once its key is rotated). Both chains verified live returning real content. Bigger fix: narrate-plant is now backed by public.plant_narrative_cache, a shared species-keyed cache — once any user's scan generates narrative content for a species, every later scan of that species by any user reads the cached row for free, no model call at all. This is the main lever for "free tier only" holding as usage grows, not just fallback depth. Residual risk: identify-plant still only has 2 providers, and Gemini's free-tier quota was found exhausted during testing (per-Google-Cloud-project, shared with narrate-plant) — a real single-fallback risk until it resets daily, tracked in ADR-0004 rather than silently accepted.
supabase/functions/identify-plant/index.ts, supabase/functions/narrate-plant/index.ts, supabase/migrations/20260807_0007_plant_narrative_cache.sql

No crash reporting or analytics

High

No Crashlytics, Sentry, or equivalent SDK anywhere in the codebase.

Consequence: once this ships, a crash on a user's device is invisible to you unless they happen to email you about it. For a first release especially, you're flying blind on stability exactly when you most need visibility.

Medium

Won't block submission, but each is a deliberate call you should make consciously rather than by default.

Four dead-code screens shipping in the binary

Resolved

IdentifyView, ProfileView, BotanicalCardDetailView deleted (verified: no dangling references left in any .swift file). The Foundry gallery is intentionally kept, confirmed properly #if DEBUG-gated end to end.

Note: ArboretumView.swift is now similarly unreachable by a real user (see the deferred-Arboretum item below), but it's explicitly commented as intentionally shelved rather than dead — same pattern this gap originally asked for.

Arboretum (map) deferred from MVP

Deliberate — Post-MVP

The Arboretum tab now routes to ArboretumComingSoonView instead of the real map, to cut pre-launch QA/perf scope ahead of the planned redesign. See ADR-0002.

Consequence: App Store listing copy was updated to drop map claims (docs/APP_STORE_LISTING.md) — must be re-added when the map ships. GPS capture on every scan is unaffected and continues regardless, so historical pins backfill automatically once Arboretum is re-enabled — confirm this stays true (see the GPS-tracking QA case in the Arboretum section above) any time the capture pipeline is touched.

Dark mode only, no light variant

Medium

Every screen forces .preferredColorScheme(.dark); no light-mode token set exists in Theme.swift.

Consequence: fine if this is an intentional brand decision (many botanical/nature apps lean dark) — but confirm it's a decision, not an oversight, since some users specifically prefer light mode for outdoor/bright-sunlight use, which is exactly when this app gets used.

Weak Dynamic Type / accessibility coverage

Medium

Only 15 of 36 view files have any accessibilityLabel/accessibilityHint at all; most type is fixed-size rather than a relative text style.

Consequence: not an automatic rejection, but it's a real quality bar you set for yourself ("Airbnb standard") and a real usability gap for VoiceOver users and anyone using larger system text sizes — currently the app would be difficult or impossible for a blind user to operate.

No CI/CD pipeline

Medium

No Fastlane config, no GitHub Actions, no build/test automation of any kind.

Consequence: every build and (eventually) every test run is manual. This compounds the "no automated tests" blocker above — even once tests exist, nothing runs them automatically on every change.
