LeafID — UI / HIG / "Liquid Glass" Review

Scope: the current main-branch dark glassmorphism UI (not the redesign/neo-brutalist branch), walked end-to-end for both a brand-new account and an account with a real saved specimen, cross-checked against iOS HIG and the app's own "Liquid Glass" design language.

Method: static code audit (grep + targeted reads across every Views/ and UI/System/ file) plus a live Simulator walkthrough — real Sign Up against production Supabase, a real photo → identify → save round trip, screenshots at each step. Session date 2026-08-11.

Important framing correction before anything else: this codebase's "Liquid Glass" (LiquidGlass.swift, GlassContainer.swift) is a hand-built .ultraThinMaterial + border glassmorphism skin, not Apple's real Liquid Glass API (glassEffect(), GlassEffectContainer) — that API is iOS 26+ only, and this project is structurally capped at the iOS 16.4 SDK (Xcode 14.3.1, per the dev-hardware constraint). This isn't a bug, just a fact that changes what "perfect execution" can mean here: judge it as a well-executed custom glass skin against general HIG translucency guidance, not against the real API's checklist (containers, morphing, .interactive(), etc. — none of that can exist in this build).

Several gaps here (Dynamic Type, dark-mode-only, weak accessibility coverage) were already tracked in qa-launch-checklist.html's Medium section — this document adds hard numbers/file citations to those and adds screen-specific findings that checklist didn't cover.

Systemic HIG gaps

Codebase-wide patterns, not one-screen bugs — each confirmed by direct grep count, not a sample.

Dynamic Type is effectively non-functional app-wide

High

142 call sites use LeafIDFont.plusJakarta(size:) / .manrope(size:) — both build on fixed-CGFloat Font.custom(_:size:) / .system(size:weight:design:), neither of which scales with the user's text-size setting. Codebase-wide search for scaling-aware font APIs (relativeTo:, Font.system(.body)-style text styles) returns exactly 1 hit.

Consequence: a user who increases their preferred text size in Settings sees zero change anywhere in this app. This is a core, first-class HIG requirement, not an edge case.
Theme/Theme.swift:201-231 (LeafIDFont), 142 call sites across Views/ and UI/System/

Reduce Motion / Reduce Transparency are ignored almost everywhere

High

Only 2 files in the entire app (ScanReticleFrame.swift, ScannerView.swift) read @Environment(\.accessibilityReduceMotion) or accessibilityReduceTransparency. Every other animation (tab switches, card transitions, the glassmorphism .ultraThinMaterial itself) runs unconditionally.

Consequence: users with motion sensitivity or transparency needs get no accommodation outside the scanner screen. LiquidGlass.swift — the one place all glass surfaces funnel through — has no Reduce Transparency handling at all, despite being the natural, single choke point to add it once for the whole app.
UI/System/LiquidGlass.swift, UI/System/GlassContainer.swift

Custom floating tab bar skips standard accessibility/motion behavior

Medium

MainTabView.swift's FloatingLiquidTabBar is a fully custom reimplementation of the primary navigation surface (not SwiftUI's TabView). Two concrete gaps versus what TabView gives for free: no .accessibilityAddTraits(.isSelected) on the active tab (VoiceOver never announces which tab is selected), and tab-switch animation uses unconditional withAnimation(.easeInOut...) with no Reduce Motion gate.

Consequence: not necessarily wrong as a design choice (the floating pill is part of the visual identity), but it trades away system-provided accessibility behavior that now needs to be manually re-added.
Views/MainTabView.swift:126-146

Icon-only buttons: mixed compliance

Context

The dedicated GlassChromeCircleButton primitive (44×44pt, forces callers to pass a real accessibilityLabel, haptic feedback) is used consistently and correctly at every real call site (Scanner, Scan Results, Botanical Card). But 11 other files use bare Image(systemName:) buttons with no accessibility label in the same file — inconsistent, not universally broken.

Good primitive exists; it's just not the only pattern in use. Worth standardizing on it rather than writing new bespoke icon buttons.
UI/System/GlassChromeCircleButton.swift vs. 11 files incl. HerbariumView.swift, DruidProfileView.swift, PaywallView.swift

Empty "Last Found" card copy is ambiguous, and ungrouped for VoiceOver

Medium

HomeEmptyLastFoundCard labels itself "LAST FOUND" (uppercase, past tense) over the instructional text "Save a specimen to your Herbarium" — for a genuinely first-time user with zero history, "Last Found" reads as if something already exists. Compare to the Herbarium empty state's clearer "No specimens yet."

Separately: the card is three ungrouped Text views plus an undecorated leaf.fill icon (no .accessibilityHidden(true)) — VoiceOver hits 4 separate swipe stops for one visual unit. The populated version of this same slot correctly wraps everything in one labeled Button — the pattern exists in-file, just not applied to the empty variant.

Fix is small: reword the empty-state copy, and add .accessibilityElement(children: .combine) + hide the decorative icon.
Views/Home/HomeView.swift:52-86

Herbarium — populated recurrent-user

Mixed-language string: "Found hace 2 minutos"

High

Confirmed live and in code. The word "Found" is a raw, unlocalized string literal concatenated with RelativeDateTimeFormatter's output — which correctly follows system locale (Spanish, in this case), producing English+Spanish mixed in one line for any non-English device.

Fix: wrap the whole interpolated string in String(localized:) so "Found" gets a real Spanish translation instead of concatenating a hardcoded English word onto a localized formatter result.
Models/Scan.swift:127-129

Druid new-user + populated, both checked

Bottom content renders behind the floating tab bar

Medium

The profile ScrollView reserves a fixed .padding(.bottom, 140) for the floating tab bar, but with the achievement grid + Support card (+ the DEBUG-only Foundry card) rendered, the last card's text visibly slides under the tab bar. Confirmed live via screenshot.

The DEBUG-only Foundry card is what pushed it over in this session's Release-equivalent content length it could still happen (achievement tiles grow over time; behavior will vary by device size). A fixed padding constant is fragile — better to measure the actual tab bar height via GeometryReader/safe-area inset rather than a hardcoded number.

GPS / location Simulator environment note

Saved specimen shows "San Francisco" instead of real location — false alarm, Simulator limitation

Not a real bug

Device log confirmed the app correctly calls real CLLocationManager and receives a real didUpdateLocations response — the code path works. The Simulator has no physical GPS; with no explicit simulated location configured (Xcode → Features → Location, or simctl location set), it falls back to Apple's default canned coordinate, which resolves to the San Francisco Bay Area regardless of the operator's real location.

Same category as the earlier gallery-picker hang: a Simulator-environment artifact, not an app defect. Would need a physical-device test (or simctl location set <lat>,<lon> before testing) to actually verify real-GPS behavior.

Druid header should show the user's real name, not "The Druid"

Requested — root cause confirmed

Not just a display fallback — this is a missing feature. displayName/realName falls back to "The Druid" when profiles.display_name is empty, and there is no TextField or edit path anywhere in the codebase to ever set a name after email/password Sign Up (only Google OAuth's full_name would auto-populate it). Every email-signup user is permanently stuck on "The Druid" today.

Real fix needs: (a) a name field on Sign Up, and/or (b) an edit-name control somewhere in Druid/Settings — not just changing the fallback string.
